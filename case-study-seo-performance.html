01

A DESIGNER WHO UNDERSTANDS THE CRAWLER
SHIPS DIFFERENT DECISIONS.

Most of the SEO and performance problems I have inherited were design decisions made without knowing the consequences: a hero image chosen without a weight budget, a heading hierarchy built for looks, a carousel that hides the only copy on the page, an infinite scroll that a crawler cannot reach.

Design decision

“Let's use a full-bleed photographic hero.”

Consequence: the hero becomes the Largest Contentful Paint element, so page speed is now a typography and cropping decision.

Design decision

“Everything below the fold loads as you scroll.”

Consequence: content injected after paint may not be indexed, and each injection risks a layout shift.

Design decision

“Two H1s look better in this layout.”

Consequence: the page loses a clear topic, and screen-reader users lose the outline they navigate by.

Accessibility, performance and SEO are the same conversation wearing different hats: can a machine — a crawler, a screen reader, a slow phone — understand this page without help?

03

ON-PAGE SEO, DONE ONCE, DONE PROPERLY.

None of this is exotic. It is a checklist applied consistently — which is exactly the part that usually gets skipped.

✓

One H1 per page, describing the pageThen a strict H2 → H3 outline, so the document has a readable structure for crawlers and screen readers alike.

✓

Unique title under 60 charactersFront-loaded with the thing being searched for: the project, then the discipline, then the name.

✓

Meta description that earns the click150 to 160 characters, written as a promise about the page rather than a keyword list.

✓

Canonical URL on every pagePrevents the same content ranking twice under /page and /page.html.

✓

Open Graph and Twitter cardsA branded 1200 × 630 card per page, generated as part of the build rather than screenshotted by hand.

✓

Descriptive alt text, empty for decorationAlt text describes the content of the artefact; purely decorative images get alt="" so they are skipped.

✓

Internal linking with real anchor text“Read the Engage case study”, never “click here”. Every case study links to two others.

✓

sitemap.xml and robots.txtEvery indexable URL listed with a last-modified date, and the sitemap declared in robots.txt.

✓

Semantic HTML landmarksnav, main, section, figure, figcaption and a skip link — structure a machine can parse.

<!-- The head block every page on this site now carries -->
<title>Engage — Enterprise Employee App Redesign | UX/UI + Frontend Case Study</title>
<meta name="description" content="End-to-end UX/UI case study: research, IA, prototyping…">

04

STRUCTURED DATA:
TELLING GOOGLE WHAT IT IS LOOKING AT.

Schema.org markup is how a page stops being “some text” and becomes “a person, who does these jobs, in this city, who published these case studies”. It is also what powers rich results and knowledge panels.

Person — name, job titles, location, skills and profiles, on the About page.
WebSite — site name and publisher, so the brand resolves consistently.
BreadcrumbList — the path from home to case studies to this page.
Article — each case study, with headline, description, image and dates.
Service — the offering list on the services page, with the area served.
ContactPage — so the enquiry route is machine-readable too.

How I validate it: Google's Rich Results Test and the Schema Markup Validator on every template, then Search Console's enhancement reports a week after deployment to catch what the crawler actually accepted.

05

PERFORMANCE IS A DESIGN BUDGET.

South African mobile data is expensive and networks are uneven. A 3 MB page is not just slow, it costs the visitor money. So the budget is set before the layout, and the design lives inside it.

Images: the whole ball game

Case-study screenshots were 1.4 to 1.6 MB PNGs. Resized to the largest size they are actually displayed at and converted to WebP at quality 82, they are 9 to 69 KB — visually identical, roughly 95% lighter.

Diagrams as SVG, not PNG

Every journey map, blueprint and pipeline diagram on this site is hand-authored SVG: a few kilobytes, infinitely sharp, and the text inside stays selectable and searchable.

Fonts: two families, preconnected

preconnect to the font host, display=swap so text is readable immediately, and no third weight added just for one heading.

JavaScript: deferred and small

All behaviour is deferred, vanilla and shared across pages, so it is parsed once and cached. No framework is loaded to run a tab component.

Lazy loading below the fold

loading="lazy" and decoding="async" on everything below the first screen; the hero image is deliberately not lazy, because that would delay LCP.

Reserve space, avoid shift

Width and height attributes or an aspect ratio on media, so nothing jumps when an image lands. CLS is a layout decision, not a mystery.

06

THE THREE NUMBERS GOOGLE ACTUALLY RANKS ON.

Core Web Vitals are the field metrics behind the score. These are the thresholds I design against, and this page measures itself against them while you read it.

LCPmeasuring…

Largest Contentful Paint — when the main thing appears. Good under 2.5 s. Usually decided by the hero image and the font strategy.

—

CLSmeasuring…

Cumulative Layout Shift — how much the page jumps. Good under 0.1. Fixed by reserving space for media, ads and late-loading fonts.

—

INPinteract to see

Interaction to Next Paint — how fast the page answers a tap. Good under 200 ms. Click a tab or a button on this page and the number appears.

—

These readings come from the browser's own PerformanceObserver, running in assets/analytics.js. No library, no third-party script, nothing leaves your device.

07

MEASUREMENT PLAN BEFORE MEASUREMENT TOOL.

Installing a tag and hoping for insight is how teams end up with dashboards nobody opens. I start from the decision I want to make, then work back to the event that informs it.

QuestionEventWhat I would change
Do people read a case study or bounce off it?chapter_view, scroll_depthMove the strongest proof above the drop-off point.
Which case study creates enquiries?cta_click with source pageFeature that story on the home page and in outreach.
Do the interactive demos earn their weight?demo_interactionCut demos nobody touches; expand the ones they do.
Is anyone stuck on the contact form?form_start, form_error, form_submitFix the field that fails most, not the field I suspect.
Is the site fast for real visitors?web_vital LCP, CLS, INPOptimise the page and device where the field data is worst.

Privacy first, by default

No cookies, no fingerprinting, no personal data. Events queue in memory and are only sent once consent is granted. Revoking consent empties the queue immediately.

Declarative tagging

Tracking lives in the markup as data-track attributes, not scattered through the JavaScript, so a new button is instrumented in one line and nothing silently breaks.

Tool-agnostic

Everything is pushed into window.dataLayer first. GA4, Plausible, Umami or a self-hosted endpoint can be attached later without touching a single page.

<!-- instrumenting a call to action: one attribute, no inline JavaScript -->
<a href="./contact.html"
   data-track="cta_click"
   data-track-location="engage-case-study-footer"
   data-track-variant="primary">Start a conversation</a>

09

WHAT I WOULD DO DIFFERENTLY.

Set the page-weight budget on day one

I compressed images after building the case studies. If the budget had been written next to the wireframes, I would have designed around it instead of retrofitting.

Instrument before launch, not after

The first weeks of traffic to a new page are the most interesting and I have no baseline for them. The event layer should ship with the page, not a release later.

Write the measurement plan with the client

The plan is far more useful when the person paying for the work agrees, up front, which number would make them change something.
